# POWER Mode — Behavioral Expectations

## Positive Activation

- **Given:** Central, federated, and open-PR models create different trust and scaling behavior.
- **Expect:** Builds three architectures, evaluates governance and failure modes at system scale, selects one, and packages it for SAFE implementation. Result: A deeply compared architecture with a bounded execution handoff.
- **Reject:** Omitting the mechanism or instead doing this: Create repository settings or publish before the chosen design is validated.

## Negative Activation

- **Given:** the task is a precise grounded execution step
- **Expect:** Remain inactive; do not begin the package-specific first step: Declare POWER, the design question, non-negotiable constraints, and exploration budget.
- **Reject:** Activating POWER Mode solely because its name appears relevant

## Precedence Or Conflict

- **Given:** Hard constraints and vetoes apply equally in broad exploration.
- **Expect:** Honor the conflict rule and preserve this invariant: bound exploration
- **Reject:** Silently violating the stated precedence for POWER Mode

## Failure Boundary

- **Given:** unbounded ideation
- **Expect:** Stop, narrow, abstain, or escalate while preserving: bounded alternatives
- **Reject:** Claiming a successful POWER Mode result past this boundary

## Strong Model Scaling

- **Given:** a capable host can compress the workflow
- **Expect:** bounded alternatives
- **Reject:** dropping the mandatory invariant

## Distinctive Mechanism

- **Given:** An ambiguous system design has several credible architectures.
- **Expect:** The skill enters a declared bounded broad-planning mode, compares architectures with QMS, collapses, and stops before consequential execution.
- **Reject:** The skill executes immediately, explores without bounds, or behaves like conservative SAFE validation.

These are provider-neutral behavioral specifications. Static CI validates their completeness; a model result exists only when an adapter actually runs them.
