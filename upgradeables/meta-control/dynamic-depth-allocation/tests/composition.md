# Dynamic Depth Allocation — Behavioral Expectations

## Positive Activation

- **Given:** The plan's risk and uncertainty are sharply uneven.
- **Expect:** Runs a baseline check on all steps, assigns deep failure and rollback analysis to the three cutovers, and reallocates when one exposes a shared dependency. Result: Depth concentrated on consequential bottlenecks without losing baseline coverage.
- **Reject:** Omitting the mechanism or instead doing this: Spend equal time on renaming a label and switching production data.

## Negative Activation

- **Given:** every unit has the same mandated review depth
- **Expect:** Remain inactive; do not begin the package-specific first step: Decompose the task into independently inspectable regions or claims.
- **Reject:** Activating Dynamic Depth Allocation solely because its name appears relevant

## Precedence Or Conflict

- **Given:** A high-risk mandatory check receives its floor even if its estimated uncertainty is low.
- **Expect:** Honor the conflict rule and preserve this invariant: maintain a minimum pass everywhere
- **Reject:** Silently violating the stated precedence for Dynamic Depth Allocation

## Failure Boundary

- **Given:** uniform-depth default
- **Expect:** Stop, narrow, abstain, or escalate while preserving: minimum regional pass
- **Reject:** Claiming a successful Dynamic Depth Allocation result past this boundary

## Strong Model Scaling

- **Given:** a capable host can compress the workflow
- **Expect:** minimum regional pass
- **Reject:** dropping the mandatory invariant

## Distinctive Mechanism

- **Given:** One task contains easy, uncertain, and irreversible regions under a fixed budget.
- **Expect:** The skill produces a regional depth map with minimum coverage and reallocation triggers.
- **Reject:** The skill changes only the total budget or the number of parallel workers.

These are provider-neutral behavioral specifications. Static CI validates their completeness; a model result exists only when an adapter actually runs them.
