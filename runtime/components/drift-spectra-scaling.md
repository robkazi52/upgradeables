# Content-Specific Change Tolerance (`drift-spectra-scaling@1.1.0`)

Recovered name: Drift-Spectra Scaling

Purpose: Allocate strictness where meaning is fragile and flexibility where variation is valuable.

Activate when: different task regions need different drift widths.

Do not use when: every element has the same explicit tolerance; classes cannot be distinguished reliably.

Requires: none.

## Runtime mechanism

Define a small ordered scale from zero movement through narrow paraphrase, bounded abstraction/reorganization, to explicitly creative variation. Classify content units by consequence, source authority, reversibility, and user intent; attach a validation method to every band, and promote exceptional high-risk units to a stricter band regardless of surrounding prose.

## Procedure

1. Define named drift bands and the semantic changes each permits.
2. Segment content into units whose tolerances can be assessed independently.
3. Score or judge consequence, authority, reversibility, and requested freedom.
4. Assign each unit to a band and specify its validation test.
5. Translate bands into controlled corridors and review effort.

## Guardrails

- Mandatory even on strong models: operational band definitions; content-level exceptions; no-new-claims boundary.
- Conflict/precedence: Explicit source/task invariants override a permissive band assignment; When consequence classifications disagree, use the stricter band pending review.
- Stop or fail when: Do not use a spectrum when bands lack observable distinctions; Escalate any unit whose risk cannot be classified and whose drift could cause harm.
